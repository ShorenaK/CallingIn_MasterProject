## Findings (judged, ordered by severity)

### B1 — Blocker: the migration creates a second `{ pairKey: 1 }` index before dropping the first

- **Where:** `backend/src/invitation-resend-migration.js:107-111`,
  `backend/src/invitation-pair-storage.js:46-51`, and
  `doc/sprint-05/invitation-resend.md:101-105`.
- **What:** the migration creates the nonunique `invitation_pair_history` index
  on `{ pairKey: 1 }` while the unique `invitation_pair_unique` index on the
  same key still exists. Only then does it drop the old one.
- **Why it is a blocker:** as far as I know, MongoDB lets two indexes share a key
  pattern only when they differ in collation or partial filter. Differing only
  in `unique` is not enough. A real server is therefore expected to reject the
  history index with an index-conflict error. The test double accepts any
  `createIndex` (`backend/test-support/resend.js:156-159`), so the tests cannot
  catch this. I have not confirmed it against a real server; that needs the
  rehearsal described below.
- **Impact:** the apply fails _safely_. Backfilled pointers remain, the legacy
  index remains, and no invitations change. Default-off startup keeps working.
  But the migration can never finish.
- **Fix:** give the history index a different key pattern, for example
  `{ pairKey: 1, createdAt: -1, _id: -1 }`. That also supports newest-first
  history for one pair. Update `verifyResendStorage` to expect that key. Make
  the test double reject duplicate key patterns, so a test fails if the
  conflict comes back.
- **Not recommended:** dropping the old index first and creating the new one
  second. If the create step fails, the database is left with neither index,
  and the current planner refuses to resume from that state.

### M1 — Medium: turning the flag off after migration is not detected or documented correctly

- **Where:** `backend/src/invitation-storage.js:84-89` and
  `doc/sprint-05/invitation-resend.md:133-136`.
- **What:** in disabled mode, startup tries to recreate the unique
  `invitation_pair_unique` index. It does not check whether the database has
  already been migrated.
  - With today's code, after a migration that history index blocks the unique
    one (see B1), so unsetting the flag makes startup fail _before any resend
    has happened_. The doc says this only happens "after history contains
    multiple invitations for a pair."
  - Once B1 is fixed, a migrated database with no resends yet would quietly
    accept the unique index again. Writers in disabled mode would then add
    first invitations without pair pointers. The database ends up half
    migrated, and the next enabled startup fails with "administrator review."
- **Fix:** in disabled mode, refuse to start if `invitationPairs` or the history
  index exists. The message should say that migrated storage needs a reviewed
  decision. Correct the rollback section to describe the real behavior.

### L1 — Low: a decline can be saved while the response reports 503

- **Where:** `backend/src/invitation-response.js:57-59` and `:82-95`.
- **What:** after the decline is written, `serializeResponse` makes a second
  read of `invitationPairs`. If that read fails, the user sees "temporarily
  unavailable" even though the decline was saved.
- **Impact:** retrying is idempotent and returns 200, so no data is wrong. The
  message is misleading, though.
- **Fix:** if the pointer lookup fails, serialize without `resendPolicy`. The
  notice is optional, so it is safe to leave out.

### Checked with no defect found (source reading)

- **Default-off behavior is preserved.**
  - Creation still uses a plain `insertOne` (`invitation-resend.js:36-38`).
  - The list projection is unchanged (`invitation-listing.js:86-88`).
  - `currentDeclineIds` returns before any database read
    (`invitation-pair-storage.js:77`).
  - Disabled 409 responses carry no new `code`.
  - The legacy unique index is still ensured.
- **The transaction design is sound in principle.**
  - Both first invitations and resends write the same pair `_id`
    (`invitation-resend.js:58-62`), so concurrent attempts should conflict.
    The driver's `withTransaction` should retry the whole callback, and the
    retry would then see the winner and return `INVITATION_ACTIVE`.
  - Server time is read again on every attempt (`:99`).
  - `InvitationConflict` is not a transient error, so it aborts the
    transaction and is returned as a 409.
  - A duplicate-key error (11000) that escapes is still treated as a conflict,
    which fails closed.
  - These are design expectations only. Nothing has run them against MongoDB.
- **Pair integrity fails closed.** These cases all stop with a logged 503:
  invitations with no pointer, a pointer to a missing invitation, a pointer to
  another pair's invitation (filtered by `pairKey`, `:81-89`), and corrupt
  decline dates (`:95-96`).
- **History is preserved.** No invitation, conversation or message is updated
  or deleted. Accepted pairs stay blocked, so a pair cannot get a second
  conversation.
- **Errors are safe and internal data stays internal.**
  - `pairKey` is projected only in enabled mode and is never serialized.
  - The frontend accepts only two allowlisted codes (`frontend/src/account/api.js:47-50`).
  - The migration CLI prints counts only and hides driver errors
    (`backend/scripts/migrate-invitation-resend.js:64-70`).
- **Participants and authentication are unchanged.** The creation route keeps
  its authentication, origin and rate-limit protections. List pointer lookups
  are limited to the page the user is allowed to see.
- **The notice and drafts behave as approved.** The sender notice text matches
  exactly and appears on outgoing cards only. Conflict messages set only
  `problem` and leave the message and recipient untouched, so drafts are kept.
- **Migration validation is thorough:** it checks topology, exactly one legacy
  index, canonical pair keys, one record per pair, statuses, decline dates,
  pointers that are never overwritten, and verification before the drop.
  Resuming before the drop is supported.
